# Differences from Kafka Streams

Flow follows Kafka Streams wherever the behaviour carries over to TypeScript: the DSL and its semantics (grace periods, retention, result timestamps, windowed key formats, `Change` propagation, deferred join results, `suppress()`), the Processor API, tasks with their own state and stream time, the commit protocol of both processing guarantees, Kafka Streams' commit metadata, and the exception handlers. This page lists where flow deliberately does something else, and why, and what is not available yet.

## Runtime

| Kafka Streams                                                                                                                   | Flow                                                                                                                                                                                                                                                                                       | Why                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `num.stream.threads` stream threads per instance, each with its own consumer, producer and poll loop.                           | One group consumer, one producer and one Node.js event loop per instance. Consumer callbacks only queue records; a scheduler processes the tasks with records concurrently (the records of one task one at a time), runs punctuators and commits between them. `numStreamThreads` is gone. | Node has one event loop: concurrency comes from overlapping the asynchronous I/O of tasks. Scale out with more instances (processes).                                |
| The Streams partition assignor: sticky, task-aware, with standby replicas and cooperative rebalancing.                          | The eager `range` assignor. A member assigned only some of the input partitions of a stateful task does not process it: it leaves and rejoins the group.                                                                                                                                   | Range keeps partition N of every co-partitioned topic on one member, which is what tasks need. A task-aware assignor with standbys is not available yet.             |
| Co-partitioning is enforced for join inputs.                                                                                    | Every stateful subtopology with several input topics (a join, but also an aggregation of merged streams) needs equal partition counts of its external topics, else `CoPartitioningError`. Repartition topics are still sized to fit.                                                       | Records of one key read from topics partitioned differently would land in different tasks, and their state would silently split.                                     |
| `exactly_once_v2`, with a transactional id per stream thread.                                                                   | `processingGuarantee: 'exactly_once'` (v2 semantics: one transaction for every task of the instance), transactional id `<applicationId>-<processId>`. A `producer.transactionalId` you set is used as it is.                                                                               | One producer per instance.                                                                                                                                           |
| `commit.interval.ms` defaults to 30000 under at-least-once.                                                                     | `commitIntervalMs` defaults to 5000 under at-least-once (100 under exactly-once, as in Kafka Streams).                                                                                                                                                                                     | Less work is repeated after a crash.                                                                                                                                 |
| A task that makes no progress for `task.timeout.ms` (commits timing out) fails its thread with a `TimeoutException`.            | After `taskTimeoutMs` of failing interval commits the instance leaves and rejoins the group, like after any other infrastructure failure; rejoins are retried without limit, with a backoff from 0.5 s to 30 s.                                                                            | A broker outage delays processing instead of stopping the application.                                                                                               |
| Stream time of windowed operators and suppression is kept in memory; after a restart it starts over from the records processed. | Partition times and the clocks of every windowed operator, join and suppression are committed with the offsets (in Kafka Streams' commit metadata format) and restored with the task.                                                                                                      | A record is late, or not, no matter where and when it is processed: a restart never accepts a record that was dropped as late before.                                |
| Changelog records carry the timestamps of the records that caused them.                                                         | Changelog records carry no timestamp (the broker's time).                                                                                                                                                                                                                                  | A window changelog (`cleanup.policy=delete,compact`) deletes by time; reprocessing old data with Kafka Streams' timestamps can delete windows the store still holds. |
| Window and session stores are segmented; expired segments are dropped.                                                          | Stores are not segmented: reads are bounded by the store's clock and retention, and expired entries are deleted as the clock advances. Windows of `emit: 'on-window-close'` are never deleted before their final result was emitted.                                                       | Restored and expired entries never change results, and no final result is lost to expiry.                                                                            |
| Global stores keep their state and a checkpoint across restarts.                                                                | Every start wipes a global table's store and loads it again from its topic.                                                                                                                                                                                                                | The topic is the source of truth: a global table's consumer commits nothing, so a reload always matches the topic.                                                   |
| `KafkaStreams.start()` returns at once; the state moves to `RUNNING` later.                                                     | `start()` resolves once every task of the first assignment is restored and running, and rejects when the start fails. States: `CREATED`, `RUNNING`, `REBALANCING`, `ERROR`, `STOPPED`.                                                                                                     | A promise is the natural readiness signal in TypeScript.                                                                                                             |
| `close()` waits without bound by default.                                                                                       | `close({ timeoutMs })` (default 20000) returns within its timeout even when the cluster is unreachable; the next owner redoes what could not be committed.                                                                                                                                 | A bounded shutdown in containers and process managers.                                                                                                               |
| Unknown configs are logged and ignored.                                                                                         | Options that were removed (`numStreamThreads`, `restartOnError`, `runEach`, `consumerRun`, `stateDir`) and consumer settings flow owns throw `FlowConfigError`.                                                                                                                            | A removed option is never silently ignored.                                                                                                                          |

## Exception Handlers

- Handlers answer `'fail'` or `'continue'`; Kafka Streams' `RETRY` answer and dead-letter queue records are not available.
- At-least-once: a send that failed with a retriable error after the producer's retries revives the affected tasks in place (they reprocess from their last commit) without asking the production handler.
- Exactly-once: a send failure never reaches the production handler. The failed send leaves the transaction unable to commit, so dropping the record could not be honoured: a retriable failure makes the instance rejoin, any other is fatal.
- A changelog record that cannot be sent cannot be dropped: `'continue'` counts as `'fail'`, since the store and its changelog would diverge.
- The uncaught exception handler answers `'shutdown'` (Kafka Streams' `SHUTDOWN_CLIENT`, the default) or `'restart'` (like `REPLACE_THREAD`: the instance abandons its group membership and joins again). `SHUTDOWN_APPLICATION` is not available.

See [Error Handling](/flow/error-handling).

## DSL

- **Options objects instead of builders.** `Consumed`, `Produced`, `Grouped`, `Materialized`, `Joined`, `StreamJoined`, `Repartitioned`, `Named`, `Branched`, `Suppressed` and its buffer configs, `EmitStrategy` and the `Stores` builders are plain options objects: `{ name }`, `split({ name }).branch(predicate, { name, chain })`, `suppress({ until, maxRecords, whenFull })`, `{ emit: 'on-window-close' }`, `Stores.keyValueStore({ name, key, value })`. The semantics are Kafka Streams'.
- **Mappers with or without the key.** Kafka Streams has separate `ValueMapper` and `ValueMapperWithKey` interfaces; flow tells them apart by the number of parameters the function declares (`mapValues`, `flatMapValues`, the joiners of stream-table and stream-global table joins).
- **Windowed results are partitioned by their base key at repartition topics too.** Kafka Streams applies the windowed partitioner only in `to()`. Flow also applies it where a windowed stream is repartitioned, so every topic of windowed records it writes is co-partitioned with the base key's other data, and key-based operations on windowed results need no repartitioning. To join windowed results with a topic partitioned by the whole windowed key, `repartition()` with a plain (non-windowed) key codec.
- **Old values after `suppress()`.** When a suppressed update goes on to an operator that needs old values (a `KTable.groupBy()` aggregation), flow sends what downstream last saw of the key as the old value; Kafka Streams sends the old value of the latest buffered update, which downstream never saw. A subtractor downstream stays consistent. See [Suppression](/flow/suppress#old-values).
- **Final results of sliding windows and sessions.** `suppress({ until: 'window-close' })` forwards a sliding window once stream time passed its end plus grace (a session: its end plus gap and grace), when it can no longer change, as `emit: 'on-window-close'` does in both. Kafka Streams' `suppress()` forwards it when stream time reaches that time, although both include their end and a record of that time still updates them (a session only when its store keeps it longer than gap plus grace), so a "final" result can be forwarded again.
- **No record cache.** Every update of a table or aggregation is forwarded, as Kafka Streams does with caching disabled (`statestore.cache.max.bytes=0`). Use `suppress()` or `emit: 'on-window-close'` for fewer updates.
- **Sliding windows** forward each window's first update once. Kafka Streams creates the right window of the previous record even when it equals the new record's left window, writes it twice and lets its record cache merge the two; without a cache flow skips the duplicate.
- **Retention 0.** A session or join store with a retention of 0 (gap, grace or time difference 0) still reads the entries of its current timestamp, so records of one timestamp merge into one session or join each other; Kafka Streams reads nothing from such a store.
- **Deferred join results.** An unmatched record of a left or outer stream-stream join is joined with `null` once a later record, of either side, moves stream time past its window and grace. Kafka Streams skips that check while the oldest pending record plus the triggering side's `after` has not passed stream time, so with asymmetric windows a closed record of the other side can wait for yet another record, and a late match meanwhile removes it. Under at-least-once, flow deletes an emitted pending record only at the next commit (as it does with suppression evictions), so a task revived or restarted from that commit emits it again instead of losing it; Kafka Streams deletes it at once.
- **One topic, several sources.** Kafka Streams rejects a topology that subscribes to a topic twice. Flow allows it (for example `stream(t)` and `table(t)`) when the sources agree on the timestamp extractor and the reset policy; they run in one task per partition.
- **Asynchronous processors.** `init()`, `process()`, `close()`, punctuators and value transformers may return promises, and `forward()` returns a promise when the downstream processors do: it must be awaited or returned before the next forward.
- **Deprecated APIs kept.** `through()`, `branch(...predicates)`, `TimeWindows.of`, `SessionWindows.withInactivityGap`, `JoinWindows.of`, `Joined.within` and the two-argument global table join still work, deprecated, with Kafka Streams' legacy semantics where Kafka Streams had them.

## Not Available Yet

- Standby replicas and a task-aware, sticky or cooperative assignor: state moves with every rebalance and is restored from changelogs.
- Interactive queries; the record cache.
- `cogroup()`, foreign-key table joins, versioned stores and stream-table join grace periods (KIP-923), `UnlimitedWindows`.
- Topology optimizations: merging repartition topics, reusing source topics as changelogs, single-store self-joins.
- Several threads in one instance; `SHUTDOWN_APPLICATION`; dead-letter queues; store-managed offsets (KIP-1035).
- Metrics beyond logs and the `kafkats:flow:process` tracing channel (see [Observability](/client/observability)).
